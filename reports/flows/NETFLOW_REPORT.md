# Flow model on NetFlow features: can one model serve both CSV files and live traffic?

Code: `layered_nids/flows/netflow.py` (raw output `netflow.json`). Data: NF-ToN-IoT-v2 test file from the earlier project (nProbe NetFlow v2 features).
Sample: 677,603 rows read; 309,834 after removing exact repeats; 81% attacks; 1,006 source hosts. The split is BY SOURCE HOST
(train 704 / validation 151 / test 151 hosts, disjoint), thresholds from validation benign flows, test scored once, one seed.

## Results (test hosts the model never saw)
- All 40 features: AUC 1.0000; recall 65.5% at the 1% policy and 96.1% at the 3% policy, with 0.0% false alarms on test.
- 24 features a packet-to-flow builder can compute exactly (sizes, counts, TCP flag union, TTL, window, duration, protocol, destination port):
  AUC 0.979; recall 60.5% (1%) and 63.9% (3%), 0.0% false alarms. By attack at the 3% policy: injection 82%, password 97%, scanning 19%, xss 59%.
- Those 24 plus derived features (individual TCP flag bits, bytes per packet, packets per second, one-way flag): AUC 0.975; recall 57.9% (1%) and 63.3% (3%);
  scanning 8%. The one improvement I declared (derived features) did NOT help: a NEGATIVE result.
- Unseen attack families (train without the family, test on it; 24 + derived features, 3% policy): injection 74.8%, password 86.5%, xss 46.7%, scanning 0%
  (only 48 test flows). Mean 52.0% over the four families that exist in the test hosts.

## How to read it
- The 1.0000 AUC is NOT evidence of a strong detector. On this dataset even unseen hosts separate perfectly with all features, which points to dataset
  artefacts (attacks are generated by a few tools and leave simple fingerprints), and only 4 of the 9 attack types fall in the test hosts. A 0.0% false-alarm rate
  on the test hosts also means their benign flows sit far below the validation tail: the validation and test hosts differ. Do not quote these numbers as real-world accuracy.
- Restricting the model to features that can be computed live costs a lot: recall at 3% false alarms falls from 96% to 64%, and scanning detection from 94% to 19%.
  The missing signal lives in features that depend on nProbe internals (application protocol, DNS fields, retransmission tracking, throughput definitions).
- Therefore: a "live" flow classifier on exactly-reproducible features is much weaker than the full-feature one. The full-feature NetFlow model is CSV-only
  (needs nProbe or a faithful reimplementation); live detection should rely on the packet detector and the rules layer.

## Limits
- One dataset, one seed, one split. No cross-dataset test (no second NetFlow dataset with the same features on disk).
- A packet-to-flow builder was NOT written: flow timeouts and several nProbe definitions cannot be checked here (no paired packets and nProbe output), so any live flow
  features would be an approximation. Not claimed.
